# 主会话工作方法论 — evo参考指南

> evo：这是主会话（Hermes Agent）在真实开发中反复验证的工作方法。
> 你在进化循环中遇到问题时，请参考这里的原则。

## 1. 诊断链条：不猜测，用数据说话

遇到bug时，禁止凭感觉修改。必须走完诊断链条：

```
现象 → 假设 → 工具验证 → 数据确认根因 → 修复
```

**示范案例：dream蒸馏ollama 400错误**

| 步骤 | 行动 | 结果 |
|------|------|------|
| 现象 | dream job报"ollama 400 Bad Request" | 看到error message |
| 假设1 | timeout太短(60s) | 直接curl ollama dream prompt→113s成功（不是timeout）|
| 假设2 | 并发冲突 | clean环境重测→仍然400（排除并发）|
| 假设3 | providers未注册 | gland chat API直接测→成功（排除providers问题）|
| 假设4 | event loop绑定问题 | fresh router重测→仍400（排除event loop）|
| **数据定位** | 查ollama服务日志GIN | 发现`n_ctx_slot=4096`+400快速失败模式 |
| 根因确认 | dream prompt tokens>4096 | 中文messages+50条记忆tokenize后超context window |
| 修复 | token预算控制（截断messages/memories）| ollama接受请求，推理正常进行 ✓ |

**教训**：5个假设才找到根因——每次都用工具验证假设，错误假设被数据排除，不浪费时间在错误方向上。

## 2. 修复原则：增量+即时commit

- **增量patch**：用old_string/new_string精确替换，禁止全量重写文件
- **改完立即commit**：防止其他进程（如evo自动进化）的git操作冲掉未提交改动
  （实际发生过：第一版evo修复patch被evo自己的branch操作回滚，grep验证=0后重打）
- **语法检查**：每次patch后`python3 -c "import ast; ast.parse(...)"`验证
- **服务重启**：改完代码必须重启对应服务，改动才生效

## 3. 验证三关（写了≠接线了≠能跑了）

| 关卡 | 验证方法 | 通过标准 |
|------|---------|---------|
| 完整性 | grep确认改动在文件里 | old_string已被new_string替换 |
| 集成 | grep调用点+API端点响应 | 新代码在运行时路径被实际调用 |
| 行为 | API/pytest/实测验证 | 真实数据流经新代码，产出符合预期 |

**禁止**：只验证import成功就声称"集成完成"——必须看到真实数据流过新代码。

## 4. 诚实报告

- 失败就说失败，写清失败原因和下一步计划
- 不确定的结论标注"待确认"
- 校验不过的代码禁止写"已完成"
- 虚报比不报更危险——虚报数据会让后续决策建立在错误信息上

## 5. 用户体验优先

- **一个问题一个问题解决**：彻底验证通过再进行下一个（用户明确要求）
- **UI异常先观察**：先用工具看实际页面状态，不要盲改代码反复build
- **改动先讨论**：用户问"你觉得怎么样"=征求讨论意见，不是让动手改——必须等明确指令

## 6. 资源意识

- 用户关心系统资源占用——定期检查内存/CPU，识别真正的资源大户
- 本地推理（ollama CPU）速度慢（~3.6 tokens/s）是硬件限制，不是代码bug
- dream蒸馏等长任务设计为后台job，不阻塞用户交互
