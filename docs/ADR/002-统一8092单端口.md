# ADR-002: ACP Proxy 统一 8092 单端口

> 日期：2026-09-01
> 状态：已接受
> 决策者：OpenMate 开发团队

---

## 背景

OpenMate 后端有多个通信层：ACP WebSocket（人↔Agent）、A2A WebSocket（Agent↔Agent）、MCP Server（Agent↔工具）、REST API（模型路由器、群组管理）。需要决定这些服务如何部署和暴露。

## 考虑的方案

### 方案A：每个服务独立端口
- 描述：ACP 用 8091、A2A 用 8093、MCP 用 8094、REST 用 8092
- 优点：职责清晰，互不影响
- 缺点：端口管理复杂，防火墙/反向代理配置多，前端需要记住多个端口

### 方案B：统一 8092 单端口
- 描述：所有服务共用 8092 端口，通过路径区分：`/ws/acp`、`/ws/a2a`、`/mcp`、`/api/*`
- 优点：部署简单，前端只需一个 base URL，反向代理配置简单
- 缺点：单点故障风险，所有流量经过一个进程

### 方案C：Nginx 反代 + 多端口
- 描述：内部多端口，Nginx 统一入口
- 优点：兼顾两者
- 缺点：增加部署复杂度，本地开发需要额外配置 Nginx

## 最终选择

**选择方案B：统一 8092 单端口**

## 理由

1. **开发效率**：本地开发只需启动一个进程，`python3 main.py` 即可
2. **前端简单**：所有 WS 和 API 都连 `ws://host:8092`，不用维护多个地址
3. **FastAPI 路由足够**：FastAPI 原生支持 WebSocket + REST 混合路由，路径区分无问题
4. **部署简单**：容器化时只需暴露一个端口
5. **未来可扩展**：如果性能不够，可以拆分为多进程 + Nginx，代码不用改

## 风险 & 后续

- 风险：单进程 GIL 限制，大量并发 Agent 时可能成为瓶颈
- 缓解：ACP Proxy 是 I/O 密集型（等待 LLM 响应），asyncio 天然适合；真不够再拆
- 后续：监控 ACP Proxy 内存和 CPU 使用情况
