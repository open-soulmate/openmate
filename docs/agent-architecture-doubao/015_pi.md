## 3. 系统架构分析

**编排模式：Turn-based ReAct（流式），且是"低阶循环 + 高阶状态机"两层分离架构。** 证据（源码确认，agent.ts）：
- **低阶**：`runAgentLoop(messages, contextSnapshot, loopConfig, onEvent, signal, streamFunction)`（`agent-loop.ts`）——纯函数式的"流式调用→工具→下一轮"循环，不持有状态。
- **高阶**：`Agent` 类——持有 `MutableAgentState`、监听集合、两个消息队列，把低阶循环产出的 `AgentEvent` reduce 进状态并广播给 listener。

**关键数据流管线**（源码确认，`createLoopConfig`）：
```
transformContext(messages, signal)   # ① 裁剪旧消息/注入外部上下文
   → convertToLlm(messages)          # ② 过滤 UI 消息、转 LLM 协议格式
   → streamFunction(...)              # ③ 流式调用模型
   → beforeToolCall → 执行工具 → afterToolCall
   → shouldStopAfterTurn / prepareNextTurn  # ④ 决定是否停/补上下文
   → getSteeringMessages()/getFollowUpMessages()  # ⑤ 注入插队/收尾消息
```

**核心组件**：
- `Agent`：状态所有者，`subscribe(listener)` 按序 await 监听器。
- `PendingMessageQueue`：`QueueMode="all"`（排空全部）或 `"one-at-a-time"`（只取队首）。
- `steeringQueue`（当前轮结束后插队）/ `followUpQueue`（Agent 本要停时再追加）。
- `AbortController`/run：每次 run 一个 `ActiveRun{promise, resolve, abortController}`。

**关键类/函数**（源码确认）：`Agent.prompt/continue/steer/followUp/abort/waitForIdle/reset`、`defaultConvertToLlm`、`createContextSnapshot`、`createLoopConfig`、`runWithLifecycle`、`handleRunFailure`、`processEvents`。

## 4. 功能拆解

- **统一 LLM 抽象（packages/ai）**：`Model` 类型归一 provider/api/baseUrl/cost/contextWindow/maxTokens；`getApiKey(provider)` 按 provider 取 key；`transport` 选择。
- **工具执行**：`toolExecution: ToolExecutionMode`（默认 `"parallel"`，一个 assistant 消息含多 toolCall 时并行执行）；`beforeToolCall/afterToolCall` 可拦截/改写工具调用。
- **事件驱动 UI**：所有活动是 `AgentEvent`（message_start/update/end、tool_execution_start/end、turn_end、agent_end），UI 订阅即渲染——与 gemini-cli/OpenHands 同思路。
- **人机干预队列**：`steer()`（插队到当前轮后）、`followUp()`（在 Agent 想停时再追一句让它继续），`hasQueuedMessages()` 探测。
- **会话**：`sessionId` 透传给提供商以命中 cache-aware 后端；`session-backends/` 包做持久化。

## 5. 技术亮点与优势

1. **循环与状态解耦**：`runAgentLoop` 是无状态纯循环，`Agent` 只管状态与事件——可单独测试/替换循环，是框架可拆用的根本。
2. **两段上下文管线（transformContext + convertToLlm）**：先裁剪/注入，再按 LLM 协议过滤 role——把"上下文工程"从模型协议里干净分离。
3. **steer/followUp 双队列 + drain 策略**：运行中安全地"插话"或"追加一轮"，且队列模式可配（一次全放 vs 一条一条）。
4. **失败即事件**：任何异常都被 `handleRunFailure` 规范化成一条 stopReason="error"/"aborted" 的 synthetic message，并完整走 message_start→…→agent_end 生命周期——UI 永不裸抛。
5. **可观测**：`packages/telemetry` 独立包 + `onPayload/onResponse` 回调 + usage（input/output/cacheRead/cacheWrite/cost）。

## 6. 稳定性机制【重点】（源码确认）

**并发/重入控制**：
- `prompt()`/`continue()`/`reset()` 都先检查 `if (this.activeRun) throw "already processing"`——同一时刻只允许一个 run；要追加必须走 `steer()`/`followUp()` 队列，杜绝并发改 transcript。
- `PendingMessageQueue.drain()` 原子地取走队列（`this.messages = this.messages.slice(...)`），避免竞态。

**失败归一化**（`handleRunFailure`，源码确认）：
- 任何异常被包成一条 `AgentMessage{stopReason: aborted|error, errorMessage}`，依次发 `message_start/message_end/turn_end/agent_end`——把"崩溃"转成"一条带错误原因的终态消息"，调用方按事件处理即可。
- `processEvents` 在 `turn_end` 时把 `errorMessage` 写进 `state.errorMessage`。

**取消**：
- 每次 run 一个 `AbortController`；`abort()` 中断；`signal` 暴露给 `beforeToolCall/shouldStopAfterTurn` 等钩子，使其能感知取消。
- `waitForIdle()` 在 `agent_end` 的所有 listener settle 后才 resolve——保证"真的空闲"再进行下一步。

**资源/边界**：
- `createContextSnapshot()` 用 `.slice()` 复制 messages/tools，外部改动不污染循环内快照。
- `processEvents` 检查 `if (!signal) throw "listener invoked outside active run"`——防止运行结束后误触发 listener。
- 工具执行默认并行，但由 `pendingToolCalls: Set<string>` 精确跟踪在途调用。

**重试**：`maxRetryDelayMs`（可选 cap 住 provider 要求的重试延迟）；具体重试退避在 `agent-loop.ts`/stream-fn 内（本文件未读，标注）。

## 7. 高可用机制【重点】（源码确认）

**容错**：`handleRunFailure` 保证 run 永远有 `agent_end`，`finishRun()` 在 `finally` 里无条件清 `isStreaming/pendingToolCalls/activeRun`——异常路径也不留脏状态。

**并发模型**：单 run + 事件队列。并行发生在**工具层**（`toolExecution:"parallel"`），不在 Agent 层；队列 drain 策略（all vs one-at-a-time）让"插话"可控。

**可观测/可扩展**：
- `subscribe` 的 listener 按序 await 并纳入 run 的 settle；事件带 model/provider/usage，天然可追踪成本。
- `packages/telemetry`、`packages/evals` 独立成包，说明把评估与遥测当一等公民。
- 多提供商归一 + `getApiKey(provider)` 按提供商取密钥，天然支持多上游容灾（虽然本文件未见自动 failover）。

**没有的**：无内置分布式/横向扩展；CLI/TUI 形态单进程。

- **可插入的自反馈钩子**：`prepareNextTurn`/`prepareNextTurnWithContext` 允许在两轮之间注入新上下文（如"根据上一步结果补文件/补检索"）；`shouldStopAfterTurn` 允许自定义停止判据——这是把"何时反思/继续"做成可插拔策略点。

## 9. openmate 可借鉴点【重点】

**P0｜"低阶无状态循环 + 高阶状态机"两层分离**
- 借鉴什么：`runAgentLoop` 纯函数循环与 `Agent` 状态/事件分离；事件流（message_start/…/agent_end）作为唯一 UI 契约。
- 怎么用：openmate 把 Agent 内核写成无状态循环，外层用事件类（含 streamId/timestamp）桥接 Web/桌面/手机三端；断线重连按事件续。
- 预期收益：多端共享同一执行内核、可独立测试内核。

**P0｜失败归一化为终态事件**
- 借鉴什么：任何异常 → synthetic message（stopReason=error/aborted + errorMessage）→ 完整生命周期。
- 怎么用：openmate 移动端 Agent 崩溃时，不要弹裸错误，而是落一条带原因的终态消息，前端据此渲染"上次失败原因"。
- 预期收益：多端错误体验一致、可恢复。

**P1｜steer/followUp 双队列 + drain 策略**
- 借鉴什么：运行中"插话"（当前轮后插入）与"追加一轮"（Agent 想停时再喂一句）分离，且支持一次全放/逐条放。
- 怎么用：openmate 桌面/手机端允许用户在 Agent 跑长任务时随时补一句，不打断当前工具执行，而在轮次间隙注入。
- 预期收益：人机协同的顺滑度。

**P1｜重入守卫 + 上下文快照拷贝**
- 借鉴什么：activeRun 存在即拒绝新 prompt（只能走队列）；传给循环的 messages/tools 用 `.slice()` 快照。
- 怎么用：openmate 多端并发发消息时用同款守卫，避免 transcript 竞态。
- 预期收益：消除多端消息交错 bug。

**P2｜transformContext + convertToLlm 两段管线**
- 借鉴什么：先做应用层上下文裁剪/注入，再做协议层 role 过滤。
- 怎么用：openmate 长任务时把"记忆注入/历史压缩"与"喂给具体模型的格式转换"解耦成两个钩子。
- 预期收益：换模型不改上下文工程。
