# 93. Generative Agents: Interactive Simulacra of Human Behavior

> **论文**: Generative Agents: Interactive Simulacra of Human Behavior (Park et al., 2023)
> **代码**: [joonspk-research/generative_agents](https://github.com/joonspk-research/generative_agents)
> **机构**: Stanford University & Google Research
> **Stars**: 22,094 | **License**: Apache-2.0

## 概述

Generative Agents 是第一个成功模拟可信人类行为的多智能体系统。25个AI代理在一个名为"Smallville"的沙盒小镇中自主生活——起床、做早餐、上班、社交、规划未来。这项工作开创性地证明了LLM驱动的代理能够产生涌现行为（emergent behavior），包括信息传播、社会关系形成和协调活动。

## 10维架构深度分析

### 1. 整体架构：Reverie 仿真框架

系统采用 **前后端分离** 的双服务器架构：

- **环境前端服务器**（Django Web Server）：基于 Phaser.js 的2D精灵游戏引擎，渲染Smallville地图，处理代理的视觉移动和交互
- **仿真后端服务器**（ReverieServer）：核心决策引擎，管理所有代理的状态、认知循环和世界时钟

核心类 `ReverieServer` 的职责：
```
ReverieServer
├── 时间管理: start_time, curr_time, sec_per_step
├── 空间管理: Maze (地图实例), personas_tile (位置映射)
├── 代理管理: personas (Persona实例字典)
├── 主循环: start_server() → 感知→决策→移动→环境更新
└── 持久化: save() → JSON序列化所有状态
```

关键设计：**仿真基于"fork"机制**——所有新仿真必须从某个基础仿真fork而来，实现了状态的版本化管理。前端通过JSON文件（`environment/{step}.json`）与后端通信，后端通过 `movement/{step}.json` 反馈代理行为。

### 2. 代理内部架构：三层认知模型

每个代理（Persona）由三个核心认知模块构成，形成 **感知→记忆→反思→规划→行动** 的完整闭环：

```
观察流 (Observations)
      ↓
┌─────────────────────────────────────┐
│         记忆流 (Memory Stream)         │
│  ┌──────────┬──────────┬──────────┐  │
│  │ 观察记录  │ 思维记录  │ 对话记录  │  │
│  │(observe) │(reflect) │ (chat)   │  │
│  └──────────┴──────────┴──────────┘  │
├─────────────────────────────────────┤
│         反思 (Reflection)              │
│  将近期记忆综合为更高层次的洞察        │
├─────────────────────────────────────┤
│         规划 (Planning)                │
│  日计划→小时计划→5分钟计划 (递归细化)   │
└─────────────────────────────────────┘
      ↓
   行动输出 (Action)
```

### 3. 记忆流（Memory Stream）：经验数据库

记忆流是代理架构的基石，存储代理的全部生活经历。每条记忆对象包含：
- **文本内容**：自然语言描述的事件/思维/对话
- **创建时间**：事件发生时刻
- **最后访问时间**：最近一次被检索的时刻
- **重要性评分**：由LLM评定的1-10分
- **嵌入向量**：用于相似度检索

三种记忆类型：
| 类型 | 说明 | 代码标识 |
|------|------|----------|
| **观察（Observation）** | 代理直接感知的事件 | `a_mem.get_str_seq_events()` |
| **思维（Thought）** | 反思生成的高层洞察 | `a_mem.get_str_seq_thoughts()` |
| **对话（Chat）** | 与其他代理的交流 | `a_mem.get_str_seq_chats()` |

### 4. 检索机制：三维评分系统

当代理需要决策时，必须从可能包含数千条记录的记忆流中检索最相关的记忆。系统使用 **三维加权评分**：

```
综合分 = w₁ × Recency + w₂ × Importance + w₃ × Relevance
```

- **Recency（时效性）**：基于最后访问时间的指数衰减函数，确保近期记忆优先
- **Importance（重要性）**：由LLM在记忆创建时评定（1-10分），反映事件的深远影响
- **Relevance（相关性）**：查询文本与记忆文本的余弦相似度，使用OpenAI嵌入模型计算

三个维度均归一化到 [0, 1] 范围，等权重（w₁=w₂=w₃=1/3）求和。最终只选取能填入prompt窗口的最佳记忆候选。

### 5. 反思机制（Reflection）：元认知

反思是系统最创新的设计之一——代理不仅能记住事件，还能 **形成更高层次的抽象认知**。

触发条件：当代理近期事件的 **累积重要性评分** 超过阈值时自动触发，实际频率约每天2-3次。

反思生成流程：
1. **提取问题**：取最近100条记忆，用prompt让LLM生成"关于这些陈述中的主体，我们可以回答的3个最重要的高层问题是什么？"
2. **检索回答**：基于生成的问题，再次从记忆流中检索相关记忆
3. **生成洞察**：用prompt让LLM推导"从以上陈述中可以推断出哪5个高层洞察？"
4. **存储反思**：将反思作为新的记忆条目存入记忆流（可被后续反思引用）

示例输出："Klaus Mueller致力于他对绅士化的研究（基于记忆1、2、8、15）"

### 6. 规划系统（Planning）：递归时间分解

规划确保代理行为的 **一致性和可信性**——没有规划，LLM可能在每一步都做出矛盾的决策（如连续三顿午餐）。

递归规划的三个层次：
```
第一层：日计划
  └── "Klaus的一天：9:00起床，10:00去图书馆，12:00午餐..."
第二层：小时计划
  └── "10:00-11:00：在图书馆查阅关于绅士化的资料"
第三层：5-15分钟计划
  └── "10:00-10:15：走到书架，找书；10:15-10:45：阅读..."
```

规划输入：代理的身份描述 + 前一天经历的摘要。规划也存储在记忆流中，可被检索和修正。

**反应式重规划**：代理持续感知环境，当观察到有意义的事件时，LLM判断是否需要偏离当前计划并重新规划。

### 7. 空间记忆（Spatial Memory）：树形世界模型

代理的空间记忆采用 **层级树结构**：

```
世界 (world)
  └── 区域 (sector)
       └── 场所 (arena)
            └── 游戏对象 (game_object)
```

代码实现中，空间记忆通过 `s_mem` 字典维护：
```python
s_mem = {
  "the Ville": {
    "Hobbs Cafe": {
      "cafe": ["cooking area", "counter", "refrigerator"],
      "kitchen": ["stove", "sink"]
    }
  }
}
```

`start_path_tester_server()` 方法通过代理的 **视觉半径**（默认8格）逐步扫描环境，构建空间记忆。代理通过空间记忆在被问及"去哪做X"时，能检索合适的地点。

### 8. 环境系统：Maze与Tile

环境由 `Maze` 类管理，地图以 **Tile网格** 表示：

每个Tile包含：
- `world`：所属世界名
- `sector`：所属区域
- `arena`：所属场所
- `game_object`：该格子上的游戏对象
- `events`：当前在该格子上的事件集合
- `collision`：是否可通行

代理移动使用 `path_finder.py` 中的寻路算法，碰撞检测基于 `collision_block_id`（值为"32125"）。代理到达目的地时，对象的动作事件会被激活（如"使用微波炉"），离开时恢复为默认空闲状态。

### 9. 代理间交互：对话与社会行为

代理间的对话系统是涌现行为的关键：

- **对话触发**：当两个代理在空间上接近且有交互动机时触发
- **对话生成**：LLM基于双方的记忆（对彼此的认知）生成自然语言对话
- **对话存储**：对话记录存入双方的记忆流
- **聊天缓冲区**：`chatting_with_buffer` 字典追踪当前对话状态，防止过早中断

信息传播机制：代理A将事件告诉代理B，代理B在后续与其他代理交互时可能传播该信息，形成社会信息级联。

### 10. 仿真控制与前端渲染

**命令行交互界面**（`open_server()`）支持丰富的调试命令：
- `run N`：运行N步仿真
- `print persona schedule X`：查看代理X的日程
- `print persona associative memory (event) X`：查看代理X的事件记忆
- `print persona spatial memory X`：查看代理X的空间记忆
- `call -- analysis X`：与代理X进行无状态对话
- `call -- load history FILE`：加载历史记录
- `save` / `fin`：保存/结束仿真

**前端渲染**：Django + Phaser.js 2D游戏引擎，支持实时观察和录像回放（`/replay/`路径）。每个仿真步生成JSON文件，前端解析并渲染代理的位置、表情符号（pronunciatio）和行为描述。

## 关键创新点

1. **记忆流 + 三维检索**：解决了LLM上下文窗口有限的问题，让代理能从海量经历中检索最相关的记忆
2. **反思机制**：实现了代理的"元认知"，从具体事件中抽象出高层洞察
3. **递归规划**：从日到小时到分钟的多粒度计划分解，确保行为一致性
4. **反应式重规划**：代理能在保持计划的同时响应环境变化
5. **涌现行为**：25个代理的长期交互产生了信息传播、社会关系、协调活动等未被显式编程的行为

## 局限性

- **计算成本高**：每个代理每步都需要多次LLM调用，25个代理一天的仿真需要数小时
- **依赖GPT-3.5**：论文写作时GPT-4尚未公开，架构设计受限于当时模型能力
- **同步仿真**：所有代理在同一时间步内顺序执行决策，未考虑异步并发
- **环境固定**：Smallville地图是静态的，不支持动态环境变化

## 对OpenMate的启示

1. **记忆系统设计**：三维检索（时效性+重要性+相关性）可直接应用于OpenMate的长期记忆管理
2. **反思机制**：定期从事件中抽象出洞察，可增强Agent的持续学习能力
3. **递归规划**：多粒度的时间规划方法适用于复杂任务的分解
4. **环境-代理分离**：前后端通过JSON文件通信的架构简洁且可扩展
5. **涌现行为**：多代理交互的涌现特性为OpenMate的多Agent协作提供理论基础
