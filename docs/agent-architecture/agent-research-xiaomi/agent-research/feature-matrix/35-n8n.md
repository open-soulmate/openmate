# n8n 深度源码功能研究（第二阶段）

研究时间：2026-09-16（cron第29轮）
源码：github.com/n8n-io/n8n（80k stars，TS monorepo，浅克隆于 /tmp/n8n，28859个文件）
仓库结构：packages/{workflow(类型/表达式), core(执行引擎), cli(服务端/模块), nodes-base(400+节点), frontend} + packages/@n8n/{task-runner, crdt, computer-use, mcp-apps, expression-runtime...}

定位说明：n8n是workflow平台不是agent，但OpenSoul will/（工作流引擎）+ OpenMate workflow页面（可视化编辑器）与其正面重合，是will/演进的最佳参照系。

## 一、执行引擎读码摘要（core/src/execution-engine/workflow-execute.ts，3168行）

### 1. 节点级容错策略（workflow/src/schemas.ts:455-487）
```ts
retryOnFail?: boolean; maxTries?: number; waitBetweenTries?: number;  // 重试三件套
onError: 'continueErrorOutput' | 'continueRegularOutput' | 'stopWorkflow';  // 三档错误语义
alwaysOutputData?: boolean;  // 空结果也输出占位
```
- continueErrorOutput：错误走节点的"错误输出端口"→ **错误处理子图**（在流程内catch）
- 工作流级 errorWorkflow：另配一个"错误工作流"+Error Trigger节点，任何失败整flow打包送入
- 对比OpenSoul：`_run_execution_async` 里节点异常→整个execution FAILED直接return，无重试无降级无错误分支

### 2. 持久化等待（Wait节点）
- `putExecutionToWait(waitTill: Date)`（interfaces.ts:1325）：执行落库状态waiting，到时由调度器/外部webhook唤醒续跑
- 执行记录持久化三开关：saveDataErrorExecution / saveDataSuccessExecution / saveExecutionProgress 按工作流配置
- execution-persistence.ts 带 pruneData 定时清理+hardDeleteBuffer
- 对比OpenSoul：engine自述"In-memory"，`_workflows/_executions`全是dict，**重启连工作流定义都丢**；cancel_execution只改status标志，`_running_tasks`存了Task却没cancel——正在跑的节点停不下来（现存bug）

### 3. 部分执行（partial-execution-utils/，12个模块）
选中任意节点重跑：directed-graph建模→find-subgraph算影响范围→**handle-cycles处理环**→recreate-node-execution-stack复用上一轮未变节点的执行数据→clean-run-data清理下游
→ OpenMate/OpenSoul完全没有；调试一条长流程不用从头重跑，是可视化编辑器的刚需体验

### 4. 表达式引擎（安全沙箱）
- `{{...}}` 表达式：tournament 解析器（@n8n/tournament）+ expression-runtime + expression-sandboxing + html-sandbox + from-AI-parse-utils
- 对比OpenSoul `_eval_condition`（will/engine.py:634）：Python `eval(expr, {"__builtins__": {}}, variables)`——注释写"Safely"但空builtins经典可逃逸（object.__class__.__mro__链），且**异常时静默返回False**：条件求值出错=静默走错分支，无告警

### 5. 分布式与并发（cli/src/）
- scaling/：Redis队列模式——job-processor消费、**multi-main-setup多主HA+leader-election选主+pubsub**、execution-stop跨进程停执行
- concurrency/：ConcurrencyControlService+ConcurrencyQueue，生产/评估各自容量令牌桶，超限排队并对外发capacity事件
- 对比OpenSoul：单进程单实例，无队列无并发控制（cosmos级别差距，自建不划算但要知道差距在哪）

### 6. 评估模块（cli/src/modules/agent-evals/）
agent-eval-case-generation.service（**LLM自动生成测试用例**）、agent-eval-rating.service（LLM评分）、agent-eval-runner.service（批量跑评估集+记录）
→ OpenSoul完全没有agent质量评估闭环。33号mem0研究、27号LiteLLM"影子评估"、本篇n8n三方独立印证：**评估集+LLM judge是生产agent平台标配**

### 7. 可观测性与运维
- insights/模块：用量分析服务+pruning任务；otel/模块：OpenTelemetry插桩；log-streaming.ee日志外送
- source-control.ee：Git环境晋升（dev→prod diff/推送）；instance-version-history：流程版本历史
- 对比OpenSoul：vital/有基础运维统计，无OTel无版本历史；52号Langfuse研究已给trace方案

### 8. 实时协作编辑（@n8n/crdt）
CRDTEngine + YjsAwareness（ChangeAction/ChangeOrigin类型化变更）+ workflow-reviews.ee评审流
→ OpenMate workflow编辑器单用户，多人同编/评审完全没有（企业售前演示场景有卖点）

### 9. 沙箱代码执行（@n8n/task-runner + task-runner-python）
代码节点(JS/Python)跑在**独立进程task runner**里，health-check-server+lifecycle管理，与主进程隔离
→ 印证32号E2B结论：OpenSoul limb/executor.py裸跑本机无隔离

### 10. 工具/MCP集成
modules/mcp（n8n作为MCP server暴露+注册表）、@n8n/mcp-apps、@n8n/computer-use（浏览器/桌面控制包）、quick-connect
→ OpenSoul已有mcp/{server,server_registry}.py基础具备，差距在MCP Apps生态

### 11. 其他
- Merge节点多模式（append/combine/chooseBranch）——多父汇聚的数据合并语义
- Execute Workflow子流程调用+workflow-as-tool（AI把流程当工具调）
- binary-data/文件系统与S3二进制管理、data-deduplication-service去重
- 触发体系：webhook/schedule/poll（poll-cursor-hooks断点轮询）；OpenSoul will/models.py定义了TriggerType.WEBHOOK但engine只实现手动execute——**触发器是声明了没接线的空架子**

## 三、源码亮点

1. **onError=continueErrorOutput 端口语义**：错误不是异常而是数据，走专门输出端口进入错误处理子图——可视化上错误处理和主流程同图可读
2. **partial-execution 的 handle-cycles**：有环图也能算"最小重跑子图"（找强连通分量处理），算法含量高（directed-graph.ts）
3. **agent-eval-case-generation**：LLM读工作流结构自动生成评估用例——评估冷启动问题的直接解法
4. **trigger是独立生命周期**：active-workflow-triggers/poll-job-manager/poll-cursor-hooks，轮询断点续拉，与执行引擎解耦
5. **模块化EE架构**：cli/src/modules/ 全是可插拔module（insights/mcp/ldap/sso...），开源核心+企业模块边界清晰——OpenSoul器官命名模块天然同构，可学其module注册模式

## 四、可复用设计（按性价比排序）

1. **【1天】节点重试**：will/models.py WorkflowNode加retryOnFail/maxTries/waitBetweenTries，_execute_node_async外包重试
2. **【1-2天】表达式安全化**：废弃eval，条件用白名单AST求值或simpleeval；异常→步骤标红+execution告警，禁止静默False（现行为=数据损坏级隐患）
3. **【2天】onError三档**：至少先做continueRegularOutput（跳过失败节点继续），错误工作流后补
4. **【2-3天】触发器接线**：TriggerType.WEBHOOK配FastAPI接收端→engine.execute_async；SCHEDULE用现有api/hermes_cron桥接
5. **【3-5天】评估闭环**：opensoul加evaluation/——测试集JSON+runner循环执行+结果表；LLM judge接cortex/quality.py
6. **【持久化之后】部分执行+版本历史**：OpenMate workflow调试体验的差异化卖点

## 五、跨研究交叉印证（三重证据链）

- 评估闭环：27-LiteLLM影子评估 + 34-LangGraph无（平台外） + 35-n8n agent-evals ⇒ OpenSoul补评估是共识
- 沙箱隔离：32-E2B + 35-n8n task-runner ⇒ limb/executor裸跑必须改
- 工作流持久化：34-LangGraph检查点 + 35-n8n execution-persistence ⇒ will/内存dict是双重确认的致命项
- 表达式安全：本篇独有新发现——OpenSoul `_eval_condition` 的eval+静默False是安全与正确性双重问题
